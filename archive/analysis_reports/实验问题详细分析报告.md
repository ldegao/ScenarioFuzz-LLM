# 实验问题详细分析报告

## 一、完成率极低的原因分析

### 1.1 数据对比

| 数据源 | answer2 | embedding | feature | hybrid |
|--------|---------|-----------|---------|--------|
| checkpoint.json中的completed_scenarios | 3 | 3 | 2 | 3 |
| metrics_records.jsonl中的记录数 | 5 | 5 | 4 | 10 |
| queue目录中的场景文件数 | 106 | - | - | - |
| 目标场景数 | 100 | 100 | 100 | 100 |

### 1.2 问题根源

**关键发现**：
- `checkpoint.json` 记录的 `completed_scenarios` 只有2-3个
- 但 `queue` 目录中实际有**106个场景文件**
- `metrics_records.jsonl` 中有5-10条记录

**结论**：
1. **场景生成成功**：系统确实生成了大量场景（至少106个）
2. **场景执行失败**：大部分场景在执行过程中失败或超时
3. **指标计算失败**：只有少数场景（5-10个）成功计算了指标
4. **checkpoint更新不及时**：checkpoint记录的场景数远少于实际处理的场景数

### 1.3 可能的原因

1. **场景执行超时**：
   - 每个场景有60秒超时限制
   - 如果场景执行时间过长，会被中断
   - 导致大量场景未完成执行

2. **CARLA模拟器问题**：
   - 模拟器可能崩溃或连接中断
   - 导致场景执行失败

3. **资源限制**：
   - 内存、CPU资源不足
   - 导致场景执行被系统终止

4. **场景验证失败**：
   - 场景可能未通过验证检查（lane check, crash check等）
   - 导致场景被丢弃

## 二、PC/PEC/TCD为0的原因分析

### 2.1 指标计算逻辑

#### PC (Parameter Coverage) 计算流程：

```python
# 从 parameter_coverage.py
def calculate_coverage(self, scenarios: List[Scenario]) -> float:
    self.covered_combinations.clear()
    
    for scenario in scenarios:
        combination = self._extract_parameter_combination(scenario)
        if combination is not None:
            self.covered_combinations.add(combination)
    
    covered_count = len(self.covered_combinations)
    if covered_count == 0:
        return 0.0  # ← 如果没有任何有效组合，返回0
```

**关键检查点**：
```python
def _extract_parameter_combination(self, scenario: Scenario) -> Optional[Tuple]:
    if not hasattr(scenario, 'state') or not scenario.state:
        return None  # ← 如果没有state，返回None
```

#### PEC (Behavior Coverage) 计算流程：

```python
# 从 driving_behavior_class_coverage.py
def calculate_coverage(self, scenarios: List[Scenario]) -> float:
    self.covered_classes.clear()
    
    for scenario in scenarios:
        if not hasattr(scenario, 'state') or not scenario.state:
            continue  # ← 跳过没有state的场景
        
        behaviors = self.classify_behavior(scenario.state)
        self.covered_classes.update(behaviors)
    
    coverage = len(self.covered_classes) / total_classes
    return float(coverage)
```

#### TCD (Trajectory Diversity) 计算流程：

```python
# 从 trajectory_diversity.py
def calculate_coverage(self, scenarios: List[Scenario]) -> Dict[str, float]:
    trajectories = self.extract_trajectories(scenarios)
    
    if len(trajectories) < 2:  # ← 需要至少2个轨迹
        return {
            'diversity_score': 0.0  # ← 如果轨迹数<2，返回0
        }
```

### 2.2 问题根源

**关键发现**：检查场景文件结构

```python
# 场景文件只包含：
{
    "events": {"crash": true, "stuck": false, ...},
    "config": {...}
}
# 没有 "state" 字段！
```

**问题分析**：

1. **场景文件缺少state数据**：
   - 场景JSON文件只包含 `events` 和 `config`
   - **没有 `state` 字段**，而所有指标计算都依赖 `scenario.state`

2. **指标计算时的场景对象**：
   - 在 `fuzzer.py` 中，指标计算使用的是内存中的 `Scenario` 对象
   - 这些对象应该有 `state` 属性（从 `ScenarioState` 对象）
   - 但如果场景执行失败，`state` 可能未正确设置

3. **为什么指标还是被记录了**：
   - 即使 `state` 为空或无效，指标计算仍然会执行
   - 但会返回默认值0.0
   - 这些0值被记录到 `metrics_records.jsonl`

### 2.3 具体原因

**PC为0的原因**：
- `_extract_parameter_combination()` 检查 `scenario.state`
- 如果 `state` 不存在或为空，返回 `None`
- 所有场景的 `combination` 都是 `None`
- `covered_combinations` 为空
- 返回 `0.0`

**PEC为0的原因**：
- `classify_behavior()` 需要从 `scenario.state` 提取参数
- 如果 `state` 不存在，跳过该场景
- 如果所有场景都没有有效 `state`，`covered_classes` 为空
- 返回 `0.0`

**TCD为0的原因**：
- `extract_trajectories()` 需要从 `scenario.state` 提取轨迹数据
- 如果 `state` 不存在或数据不完整，无法提取轨迹
- 如果有效轨迹数 < 2，直接返回 `0.0`

## 三、BCM值完全相同的原因分析

### 3.1 BCM计算逻辑

```python
# 从 behavior_matrix.py
def calculate_coverage(self, scenarios: List[Scenario]) -> Dict[str, float]:
    matrix = self.build_matrix(scenarios)
    
    # 计算唯一行为组合数
    unique_combinations = set()
    for j in range(matrix.shape[1]):
        combination = tuple(matrix[:, j])
        unique_combinations.add(combination)
    
    covered_count = len(unique_combinations)
    total_possible = 2 ** 12  # 12种行为，2^12 = 4096
    
    # 对数归一化
    coverage_ratio = np.log1p(covered_count) / np.log1p(total_possible)
    return {'coverage_ratio': coverage_ratio}
```

### 3.2 验证BCM值

**计算验证**：
```python
import numpy as np
# 如果所有场景的行为组合都相同（只有1种唯一组合）
covered_count = 1
total_possible = 4096
coverage_ratio = np.log1p(1) / np.log1p(4096)
# = log(2) / log(4097)
# ≈ 0.0833308877281607
```

**结果匹配**：所有场景的BCM值都是 `0.0833308877281607`，正好等于 `log(2)/log(4097)`

### 3.3 问题根源

**关键发现**：所有场景的行为标签都相同

可能的原因：

1. **所有场景都触发了相同的行为**：
   - 比如所有场景都只有 `stuck` 行为
   - 或者所有场景都只有 `following` 行为
   - 导致行为矩阵的每一列都相同

2. **行为标签提取逻辑问题**：
   - `label_behaviors()` 函数可能对所有场景返回相同的标签集合
   - 比如所有场景都没有触发任何行为（空标签集合）
   - 或者所有场景都只触发了同一种行为

3. **场景执行状态相同**：
   - 如果所有场景都在执行早期失败（比如都stuck）
   - 或者所有场景都执行了相同的简单行为
   - 会导致行为标签相同

### 3.4 验证假设

**检查场景文件**：
- 场景文件中的 `events` 字段显示：
  - `crash: true`
  - `stuck: false`
  - `lane_invasion: false`
  - 其他都是 `false`

**可能的情况**：
- 如果所有场景都在早期就crash了
- 那么所有场景的行为标签可能都是 `['collision']`
- 导致所有场景的行为组合相同
- BCM = log(1+1)/log(1+4096) = 0.0833

## 四、数据存储与统计结果的关系

### 4.1 数据流分析

```
场景生成 → 场景执行 → 状态收集 → 指标计算 → 记录保存
   ↓           ↓          ↓          ↓          ↓
 queue/    执行结果    state对象   指标值    metrics_records.jsonl
```

### 4.2 问题链路

1. **场景生成阶段**：
   - ✅ 成功：生成了106个场景文件

2. **场景执行阶段**：
   - ❌ 失败：大部分场景执行失败或超时
   - 只有少数场景（5-10个）成功执行

3. **状态收集阶段**：
   - ❌ 失败：即使场景执行了，`state` 数据可能未正确收集
   - 或者 `state` 数据不完整

4. **指标计算阶段**：
   - ⚠️ 部分成功：指标计算代码执行了
   - 但由于 `state` 数据缺失，返回默认值0.0
   - BCM由于所有场景行为相同，返回固定值0.0833

5. **记录保存阶段**：
   - ✅ 成功：指标值（即使是0）被正确保存到 `metrics_records.jsonl`

### 4.3 为什么统计结果是这样

**PC/PEC/TCD = 0.0**：
- 因为所有场景的 `state` 数据缺失或不完整
- 指标计算无法提取有效数据
- 返回默认值0.0

**BCM = 0.0833（固定值）**：
- 因为所有场景的行为标签都相同
- 只有1种唯一的行为组合
- BCM = log(1+1)/log(1+4096) = 0.0833

**完成率低**：
- checkpoint记录的完成场景数（2-3个）远少于目标（100个）
- 实际执行的场景数（5-10个）也远少于目标
- 说明实验在早期就停止了或大量场景执行失败

## 五、问题总结与建议

### 5.1 核心问题

1. **场景执行失败率高**：106个场景中只有5-10个成功执行
2. **状态数据缺失**：场景文件缺少 `state` 数据，导致指标无法计算
3. **行为多样性不足**：所有场景的行为标签相同，导致BCM值固定
4. **checkpoint更新不及时**：checkpoint记录的场景数不准确

### 5.2 修复建议

#### 立即行动：

1. **检查场景执行日志**：
   ```bash
   find experiment_results/SimilarityComparison -name "*.log" -exec grep -i "error\|timeout\|failed" {} \;
   ```

2. **检查state数据收集**：
   - 确认 `scenario.state` 是否正确设置
   - 检查 `ScenarioState` 对象是否在场景执行后正确保存

3. **检查指标计算时机**：
   - 确认指标计算是在场景执行完成后进行的
   - 确认 `state` 数据在指标计算时已经可用

#### 长期修复：

1. **改进错误处理**：
   - 记录场景执行失败的原因
   - 区分不同类型的失败（超时、崩溃、验证失败等）

2. **改进数据收集**：
   - 确保 `state` 数据在场景执行后正确保存
   - 在场景文件中包含完整的 `state` 数据

3. **改进checkpoint机制**：
   - 实时更新checkpoint
   - 区分"生成"、"执行中"、"已完成"等状态

4. **增加调试信息**：
   - 在指标计算时记录详细的调试信息
   - 记录为什么某些指标返回0

### 5.3 验证方法

1. **检查单个场景的执行**：
   - 手动运行一个场景，确认 `state` 数据是否正确收集

2. **检查指标计算**：
   - 使用有完整 `state` 数据的场景测试指标计算
   - 确认指标值是否正常

3. **检查行为标签**：
   - 手动检查几个场景的行为标签
   - 确认为什么所有场景的行为标签相同
